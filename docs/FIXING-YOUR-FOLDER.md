# Fixing your folder, and pushing to GitHub properly

Two problems, both easy to fix.

---

## Problem 1 — loose files at your project root

Earlier in this project I showed you individual files. Downloading those puts
a copy at the **root** of your folder, where it does nothing — the real one is
already nested inside `src/`, `docs/` or `supabase/`.

One of them is actively harmful: a `middleware.ts` at the root. That file was
renamed to `src/proxy.ts` in Next 16, and if both exist Next may load the old
one, breaking your locale routing.

### What your root should contain — exactly this, nothing else

```
touruae/
├── .gitignore
├── .env.example
├── .env.local.example
├── .env.local          ← yours, holds your keys, NEVER committed
├── README.md
├── next-env.d.ts
├── next.config.ts
├── package.json
├── package-lock.json
├── postcss.config.mjs
├── tsconfig.json
├── vercel.json
├── docs/
├── public/
├── src/
├── supabase/
├── node_modules/       ← generated by npm install, NEVER committed
└── .next/              ← generated by npm run dev, NEVER committed
```

**Anything else at the root is a stray. Delete it.**

### The fastest fix (recommended)

Start clean. This takes two minutes and removes any doubt:

1. Copy your `.env.local` somewhere safe (Desktop). It has your keys.
2. Delete the entire project folder.
3. Extract the ZIP fresh.
4. Copy `.env.local` back in.
5. `npm install`

### Or run the cleanup script

If you'd rather not start over, `cleanup.ps1` is in the ZIP root. From inside
your project folder:

```powershell
powershell -ExecutionPolicy Bypass -File cleanup.ps1
```

It deletes only known strays and lists what should remain. It will not touch
`src/`, `supabase/`, `docs/`, `public/` or your `.env.local`.

### Delete these by hand if you prefer

```
middleware.ts    proxy.ts        layout.tsx      page.tsx
globals.css      session.ts      auth.ts         mnt-list
company-application.ts           review-application.ts
application-review-card.tsx      0008_supplier_applications.sql
03_actor_boundaries.sql          ACCESS-CONTROL.md
GETTING-STARTED.md               VERIFICATION.md
mnt\  (folder)
```

Every one of these already exists in its correct place inside the project.

**About `.env`:** you have both `.env` and `.env.local`. Next.js reads
`.env.local`. Open `.env`, move anything you need into `.env.local`, then
delete `.env`. I'm not scripting that one because it may hold your keys.

## Problem 2 — `node_modules` and GitHub

You're right to worry. `node_modules` is roughly 400 MB and hundreds of
thousands of files. GitHub rejects pushes over 100 MB per file and will crawl
or fail on a repo that size.

**It's already handled.** The `.gitignore` in this project excludes
`node_modules/`, `.next/` and every `.env` file. Git will skip them
automatically.

### Check before your first push

```powershell
git add .
git status --short | Select-String "node_modules|\.next" 
git status --short | Select-String "\.env" | Select-String -NotMatch "example"
```

Both must print **nothing**.

`.env.example` and `.env.local.example` *are* committed on purpose — they are
empty templates showing which variables exist, with no values in them. Your
real `.env.local` is excluded, which is why the second command filters
`example` out.

Verified: with 500 files in `node_modules`, a `.next` folder and a
`.env.local` containing a service-role key, a real `git add .` staged
**10 files** and none of the excluded ones.

### If you already committed node_modules

Symptoms: `git status` lists thousands of files, or a push fails on size.

```bash
git rm -r --cached node_modules
git rm -r --cached .next
git rm --cached .env.local
git commit -m "Remove generated files from tracking"
```

`--cached` removes them from Git but **keeps them on your disk** — your
project keeps working.

If a push already failed because of a large file, the simplest fix is to start
the history over. You lose your commit history, not your code:

```bash
Remove-Item -Recurse -Force .git
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/YOUR-NAME/YOUR-REPO.git
git push -u origin main --force
```

## The full push, start to finish

```bash
# 1. From inside your project folder
cd C:\Users\Zbook\Downloads\seo\tour\touruae

# 2. Stage everything, then confirm nothing dangerous went in
git add .
git status --short | Select-String "node_modules|\.next"
git status --short | Select-String "\.env" | Select-String -NotMatch "example"
#    ↑ both must print nothing

# 3. Commit
git commit -m "TravelHub Gulf"

# 4. Push
git branch -M main
git remote add origin https://github.com/YOUR-NAME/YOUR-REPO.git
git push -u origin main
```

A healthy first commit is **around 200 files**, not 200,000. If `git add .`
takes more than a few seconds, stop — `node_modules` is being included, and
something is wrong with your `.gitignore`.

## Then deploy on Vercel

1. <https://vercel.com> → sign in with GitHub
2. **Add New → Project** → Import your repository
3. Change no settings. Vercel detects Next.js on its own.
4. **Deploy**

Vercel runs `npm install` on its own servers, which is exactly why
`node_modules` must not be in the repo.

Add your environment variables in **Settings → Environment Variables**, then
redeploy — variables only apply to builds that run after you add them. Full
list in Part 3 of `GETTING-STARTED.md`.

## One rule that prevents this happening again

**Only ever use the ZIP.** Extract it over your project folder and let it
overwrite. Individual files are for reading in the browser, not for
downloading — a file downloaded on its own lands at the root, detached from
the folder it belongs in.

## Vercel build or database troubleshooting

### "LF will be replaced by CRLF" warnings on `git add`

Harmless. Git is normalising line endings between Windows and Linux. The
project now ships a `.gitattributes` that settles the rule, so these stop
after your next commit. Nothing was broken.

### The site deploys but shows "Demo mode"

The commonest cause by far: **the build ran before you added the environment
variables.** Vercel bakes them in at build time, so adding them afterwards
changes nothing until you rebuild.

1. Vercel → **Settings → Environment Variables**
2. Confirm `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` and
   `SUPABASE_SERVICE_ROLE_KEY` are all present
3. Tick **Production, Preview and Development** for each
4. **Deployments → ⋯ → Redeploy**

### The site deploys but pages are empty

Environment variables are set, but the SQL has not been run. In the Supabase
**SQL Editor**, run `supabase/migrations/0001` through `0012` in order, then
`supabase/seed/seed.sql`. Check **Table Editor** afterwards: `countries`
should have 6 rows.

### The build itself fails

Read the **first** error in the Vercel log, not the last — everything after it
is usually a consequence. Then check:

| Log says | Cause |
|---|---|
| `Module not found` | A file did not upload. Confirm `src/` is in your GitHub repo. |
| `Couldn't find any 'pages' or 'app' directory` | A stray lockfile in a parent folder — see the top of this guide. |
| `Type error:` | A real code error. Send me the file and line. |
| Anything mentioning `supabase` | Usually a wrong URL or key. Copy them again from Project Settings → API. |

The build is deliberately resilient to a database that is unreachable or not
yet migrated: `generateStaticParams` catches the failure, logs a warning, and
prerenders nothing rather than failing the deployment. Verified by building
with a deliberately unreachable Supabase URL.

### "Hobby accounts are limited to daily cron jobs"

Fixed in `vercel.json`, which no longer defines any cron jobs. Scheduled work
moved into Postgres via `pg_cron` — see "Scheduled jobs" in `DEPLOYMENT.md`.
Pull the latest files, commit and redeploy.

**Do not simply change the schedule to daily.** The seat-hold reaper releases
abandoned checkout seats within 15 minutes; running it once a day would make
seats unsellable for up to 24 hours.
